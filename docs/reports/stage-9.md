# Отчёт: этап 9 — hardening (срезы 9.1, 9.2, 9.3)

## Что сделано
**9.1 Защита веб-слоя**
- **Защитные заголовки**: API — `X-Content-Type-Options`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy`, `Cache-Control: no-store`; фронтенд — CSP (только свои источники, `frame-ancestors 'self'`, без чужих фреймов), `Permissions-Policy`, HSTS включается переменной `ENABLE_HSTS=1` при сборке за TLS. Проверено на живом стенде (curl).
- **Ограничение частоты запросов** (Redis, без Redis — память процесса; при сбое хранилища запросы **пропускаются**, пишется предупреждение): регистрация 10/час и вход 30/10 мин по IP, приглашения 60/10 мин по IP, загрузки 60/10 мин и выгрузки CSV 30/10 мин по пользователю, общий потолок 1200/мин по пользователю; ответ 429 `rate_limited` с `Retry-After` и correlation id. Ограничение входа по email (5 неудач/15 мин) работает отдельно. На стенде разработки выключено по умолчанию (все запросы E2E с одного адреса); в рабочей среде включить `RATE_LIMIT_ENABLED=true` и `TRUST_PROXY_HEADERS=true` за прокси.
- **Аудит выгрузок**: четыре CSV (оборотно-сальдовая, банк: сводка / сопоставления / операции) пишут событие `export.created` (кто, отчёт, период, счёт, число строк); содержимое выгрузки и текст назначений в аудит не попадают. Это был пропуск, найденный при проверке на соответствие ТЗ §13.

**9.2 Эксплуатация**
- `/metrics` (Prometheus: число запросов и гистограмма длительности по методу, **шаблону маршрута** и классу статуса; идентификаторы организаций в метки не попадают; доступ только с `METRICS_TOKEN`, без токена — 404); `/ready` проверяет БД и Redis.
- **Резервная копия и проверка восстановления** (`infra/backup/backup.sh`, `verify-restore.sh`): БД (pg_dump custom), файлы документов, манифест с SHA-256 и версией миграций, ротация. **Реально выполнено на сервере**: копия → проверка сумм → восстановление во временную БД → числа строк совпали во всех таблицах → инварианты (проводки сбалансированы, остатки = сумма движений, сопоставления банка ≤ операций) выполнены → версия миграций 0018 → распаковка файлов (103 файла). Выявлено и исправлено: архив файлов создавался от root (права).
- **Нагрузочный тест** (`scripts/loadtest.py`, 4 ядра ВМ на HDD, генератор нагрузки на той же ВМ): 5 параллельных запросов — худший p95 **114 мс**; 20 параллельных, 1 процесс — ~65 запросов/с, худший p95 **512 мс** (ориентир ТЗ < 500 мс **не выполнен** при такой нагрузке); 20 параллельных, 3 процесса (`UVICORN_WORKERS=3`) — ~124 запросов/с, худший p95 **284 мс** (выполнен). Вывод: один процесс упирается в процессор, рабочая среда должна запускаться минимум с 2–3 процессами; цифры ориентировочные (HDD, общий хост).
- Документ «Эксплуатация» (`docs/14-operations.md`): запуск, наблюдаемость и предлагаемые оповещения, копии и восстановление, откат версии, политика хранения, реагирование на инциденты, чек-лист приёмки (UAT).

**9.3 Второй фактор (TOTP)**
- Алгоритм RFC 6238 без внешних библиотек (проверен векторами RFC); секрет шифруется (Fernet, ключ `APP_SECRET_KEY`, в БД ключа нет); 8 одноразовых кодов восстановления (хранится только SHA-256); повтор кода того же интервала отклоняется; неверные коды считаются в тот же лимит попыток входа (перебор 6 цифр ограничен); включение, выключение и выпуск новых кодов требуют пароль и код; вход: пароль → запрос кода → сессия.
- Политика «обязателен для владельцев и администраторов» включается настройкой `MFA_REQUIRED_FOR_ADMINS` (по умолчанию выключена — «поэтапно» по ТЗ §13); без второго фактора такие пользователи получают 403 `mfa_required_for_admins`, раздел «Безопасность» остаётся доступен.
- Интерфейс: блок «Двухфакторная защита» в «Безопасности» (ключ текстом и ссылка otpauth; QR-кода нет), поле кода на странице входа; uz/ru/en.

## Что НЕ реализовано / ограничения
- **Резервные копии лежат на том же сервере**: вынос за пределы сервера, расписание (cron) и мониторинг свежести копии не настроены — решение и бюджет владельца (R17).
- **Внешний мониторинг и оповещения не настроены** (нужна площадка); `/metrics` по процессу — при нескольких процессах каждый отдаёт свои счётчики.
- CSP содержит `'unsafe-inline'` для скриптов (особенность Next.js; строгий CSP с nonce — отдельная задача).
- Ограничитель частоты: числа предварительные; при `TRUST_PROXY_HEADERS=false` за прокси все пользователи для него — один адрес.
- Второй фактор: нет QR-кода, нет WebAuthn/ключей безопасности, политика администраторов — глобальная настройка, а не на уровне организации; смена `APP_SECRET_KEY` делает секреты нечитаемыми.
- Нет экспорта данных организации и удаления организации/диалогов AI по запросу; нет автоматической очистки старых попыток входа и сессий.
- Нагрузка проверена только на чтение и на малом объёме данных; запись, AI-задачи и 20 параллельных фоновых задач (ТЗ §14) не измерены; SLA/RPO/RTO не утверждены.
- Откат схемы миграций «вперёд» (описан в документе), автоматического отката нет; UAT не проводился.
