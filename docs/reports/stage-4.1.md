# Срез 4.1 — складское ядро (количества)

План и границы этапа: [docs/08-stage4-plan.md](../08-stage4-plan.md). Только количества: **стоимости запасов, себестоимости и проводок нет** (нет утверждённой учётной политики, Q9/Q26).

## Что сделано
- **Операции**: приход, расход, перемещение. Черновик → «Провести». Черновик можно править и удалять (с контролем версии), проведённая операция неизменяема.
- **Движения** (`stock_movement`) — только добавляются: триггер БД запрещает UPDATE/DELETE даже владельцу БД, роли приложения выданы лишь INSERT/SELECT. Перемещение = два движения одной операции.
- **Остатки** (`stock_balance`) — производная таблица, меняется только вместе с движением, под блокировкой строк в стабильном порядке (без взаимных блокировок). Количество — `NUMERIC(20,6)`, в API строкой, без float; запись `1e3`, `+1`, `.5` не принимается.
- **Проведение**: операция блокируется на время проведения, повтор → 409 `operation_already_posted`; нехватка → 409 `insufficient_stock` с перечнем (артикул, есть, нужно), ничего не меняется. Одинаковый товар в нескольких строках проверяется суммарно.
- **Политика отрицательных остатков** — настройка организации, по умолчанию «запрещено» (меняет только право `org.manage`, пишется в аудит).
- **Сверка**: «остаток = сумма движений» по каждой паре (склад, товар): API `/stock/reconciliation` и баннер на странице остатков.
- **Склад с ненулевым остатком нельзя архивировать** (правило, отложенное с этапа 2).
- **Интерфейс**: разделы «Остатки» (фильтры, поиск, сортировка, переход к истории), «Операции», «Движения», редактор операции, на uz/ru/en; права `stock.read/manage/post` (матрица — предложение, Q24).
- Побочная находка: числа в API формата `1e3` принимались как 1000 (цены, количества документов, количества склада) — исправлено общим валидатором.

## Проверки (реальные результаты)
| Проверка | Результат |
|---|---|
| pytest на сервере (Postgres, SeaweedFS, Redis) | **356 passed** |
| Playwright, desktop + Pixel 7, полный прогон | **70 passed** (4,7 мин) |
| vitest | 33 passed |
| ruff, ruff format, mypy --strict, import-linter, eslint, tsc, pip-audit | без замечаний |

Покрыто: матрица 7 ролей × (чтение, черновики, проведение); приход/расход/перемещение и итоговые остатки и движения; нехватка без побочных эффектов; суммарная проверка по строкам; политика отрицательных; двойное проведение и **5 параллельных проведений одной операции → ровно одно**; **16 параллельных расходов при остатке 10 → ровно 10 успешных, остаток 0, ни разу в минус**; встречные перемещения из 6 потоков без взаимных блокировок; точность 6 знаков; валидация (услуга, чужой товар/склад, архивные, 0/минус/7 знаков/экспонента/float); пере-проверка ссылок при проведении; правка черновика, конфликт версий, удаление; запрет архива склада с остатком; списки (фильтры, поиск, сортировка, пагинация); **неизменяемость движений на уровне БД**; обнаружение подделанного остатка сверкой; изоляция организаций и RLS.

**Найдено проверками и исправлено**: числа в экспоненциальной записи (см. выше); правка черновика с неверным складом давала 500 вместо 422 (автосброс сессии упирался в ограничение БД) — теперь итоговое состояние проверяется до изменения объекта; при сборке стека пересобирался не весь набор образов (миграция не применилась на сервере) — выявлено E2E.

## Что НЕ реализовано / ограничения
- Нет стоимости и проводок; нет коэффициентов между единицами (движение всегда в единице товара, Q27).
- Нет сторно проведённой операции, возвратов, инвентаризации, резервов, минимального запаса (срезы 4.2–4.3), нет создания операций из документов (4.2).
- Операции по дате: дата не проверяется на закрытые периоды (периодов ещё нет, этап 5); разрешена любая дата.
- Сверка выполняется по всей организации при открытии страницы остатков: на больших объёмах потребуется оптимизация (до нагрузочных замеров этапа 9 не заявляю производительность).
- Серийные номера и партии не ведутся (Q28).
- Переводы uz/en мои, носитель не проверял.
- Изменения закоммичены локально, в GitHub не отправлены.
