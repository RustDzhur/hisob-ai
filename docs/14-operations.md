# Эксплуатация Hisob AI

Документ описывает, как запускать, наблюдать, копировать, восстанавливать и откатывать систему. **Значения RPO/RTO, сроки хранения и пороги оповещений — предложения для утверждения владельцем (R17)**, не принятые решения.

## 1. Запуск в рабочей среде
- `docker compose up -d` (сервисы: postgres, storage, redis, worker, migrate, backend, frontend). Миграции применяет сервис `migrate` перед стартом backend.
- Обязательные настройки (файл `.env`, в репозиторий не попадает): пароли БД, ключи хранилища, `COOKIE_SECURE=true` (только за TLS), `RATE_LIMIT_ENABLED=true`, `TRUST_PROXY_HEADERS=true` — если перед системой обратный прокси (иначе все пользователи для ограничителя — один адрес), `METRICS_TOKEN` (иначе `/metrics` отключён), ключ AI-провайдера (только у воркера).
- Масштабирование: `UVICORN_WORKERS` (замер на 4 ядрах: 1 процесс ≈ 65 запросов/с, 3 процесса ≈ 124 запросов/с при 20 параллельных запросах, см. отчёт этапа 9). Ограничитель частоты при Redis общий для процессов; метрики `/metrics` — **по процессу** (при нескольких процессах собирать по каждому реплике/порту или перейти на multiprocess-режим — не сделано).
- Заголовок HSTS включается переменной `ENABLE_HSTS=1` **при сборке фронтенда** за TLS.

## 2. Наблюдаемость
- `/health` (жив), `/ready` (БД и, если настроена очередь, Redis), `/metrics` (Prometheus: `hisob_http_requests_total`, `hisob_http_request_duration_seconds`; метки — метод, шаблон маршрута, класс статуса).
- Журналы: JSON, у каждого запроса `correlation_id` (возвращается клиенту в `X-Correlation-ID`); пользователю при ошибке показывается этот идентификатор.
- **Предлагаемые оповещения** (настроить в системе мониторинга площадки): `/ready` ≠ 200 более 2 минут; доля 5xx > 2 % за 5 минут; p95 длительности чтения > 500 мс 10 минут; свободное место на дисках БД и хранилища < 20 %; резервная копия старше 26 часов; рост `rate_limited` (429) и `auth.login_failed` в аудите.

## 3. Резервное копирование и восстановление
- **Копия**: `infra/backup/backup.sh [каталог]` — `pg_dump` (формат custom), архив тома файлов документов, манифест с SHA-256 и версией миграций; хранится `BACKUP_KEEP` (14) последних.
- **Проверка восстановления**: `infra/backup/verify-restore.sh <каталог_копии>` — сверяет суммы, разворачивает БД во **временную** базу (рабочая не затрагивается), сравнивает числа строк по всем таблицам, проверяет инварианты (проводки сбалансированы, остатки = сумма движений, сопоставления банка не превышают операции), распаковывает файлы. Выполнена на сервере (см. отчёт этапа 9).
- **Предложение (R17)**: копия раз в сутки (cron на сервере), RPO ≤ 24 ч, RTO ≤ 4 ч; **копия должна уходить за пределы сервера** (другой хост/облако) — это решение и бюджет владельца; проверка восстановления — не реже раза в месяц и после каждого изменения схемы.
- **Восстановление в рабочую БД** (авария): остановить backend и worker; создать пустую БД и выполнить `pg_restore` из `db.dump` под ролью владельца; распаковать `storage.tar.gz` в том `storage-data`; запустить `migrate` (приведёт схему к текущей версии), затем остальные сервисы. Данные Redis не восстанавливаются (очередь, истина — в PostgreSQL).
- Данные организаций в копиях не обезличиваются: хранить с тем же уровнем защиты, что и рабочую БД; файлы копий — права 600.

## 4. Откат версии
1. Перед обновлением — свежая резервная копия (п. 3).
2. Образы тегируются версией; откат кода — запуск предыдущего тега.
3. **Миграции схемы — «вперёд»**: `downgrade` написаны, но не гарантируют сохранность данных новых таблиц. Если новая версия применила миграцию, откат кода без отката схемы допустим только когда новая схема обратно совместима (добавляет таблицы/колонки); иначе — восстановление из копии п. 3 и потеря данных после неё. Поэтому миграции выпускаются так, чтобы предыдущая версия кода работала с новой схемой.
4. После отката: `/ready`, E2E-проверка входа и открытия основных разделов.

## 5. Политика хранения и удаления (предложение, R17)
| Данные | Срок | Примечание |
|---|---|---|
| Проводки, документы, банковские операции, склад | пока организация активна; после закрытия — по требованиям законодательства о хранении учётных документов (**срок определяет бухгалтер/юрист**, не задан) | проведённое неизменяемо, исправление — сторно |
| Журнал аудита | не менее 5 лет (предложение) | только добавление |
| Сессии | 14 дней, затем недействительны | отзыв выходом и сменой пароля |
| Попытки входа | 90 дней (очистка не автоматизирована) | |
| Диалоги AI-помощника | по запросу пользователя/организации (кнопки удаления нет — **не реализовано**) | текст вопросов в аудит не пишется |
| Резервные копии | `BACKUP_KEEP` последних (по умолчанию 14) | |
- **Экспорт данных организации и удаление организации по запросу не реализованы** (нужны решение о составе выгрузки и юридическая проверка; пункт к обсуждению).

## 6. Реагирование на инциденты (минимум)
1. Зафиксировать время и `correlation_id`; оценить объём (какие организации, какие данные).
2. Ограничить: отозвать сессии затронутых пользователей, сменить ключи (БД, хранилище, AI, `METRICS_TOKEN`), при необходимости остановить доступ (`docker compose stop frontend`).
3. Восстановить из копии при порче данных; сверить инварианты `verify-restore.sh`.
4. Уведомить владельца организации; персональные данные — по требованиям законодательства (проверяется юристом, Q4).
5. Разбор: причина, что поменять (тест, ограничение, оповещение).

- [ ] Юридически решён вопрос передачи данных внешнему AI (Q4, R16).
- [ ] Права ролей подтверждены владельцем (R1, R3, R8, R13, R15, R16).
- [ ] Настроены TLS, `COOKIE_SECURE`, ограничитель частоты и доверие к прокси, `METRICS_TOKEN`, оповещения.
- [ ] Настроены ежедневная копия и вынос её за пределы сервера; пройдена проверка восстановления.
- [ ] Нагрузочная проверка на целевом железе (SSD, не HDD, R9) с реальными объёмами.
