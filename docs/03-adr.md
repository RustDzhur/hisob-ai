### ADR-001 Модульный монолит
**Контекст.** ТЗ §6 требует начать с монолита. **Решение.** Один backend-процесс (+ воркер того же образа), модули с чёткими границами. **Последствия.** Просто деплоить и проводить транзакции через модули; дисциплина границ обязательна (ADR-004).

### ADR-002 PostgreSQL — источник истины
PostgreSQL 16, SQLAlchemy 2, Alembic. Redis — очередь/лимиты/кэш, потеря Redis не должна терять финансовые данные. Файлы — S3-совместимое хранилище (SeaweedFS в dev: MinIO больше не публикует образы). Состояние фоновых задач — в таблице `ai_job` в PostgreSQL (источник истины); Redis — только брокер Dramatiq, метаданные и hash — в БД.

### ADR-003 Аутентификация
Серверные сессии (opaque token, в БД только SHA-256), cookie HttpOnly/Secure/SameSite=Lax, CSRF double-submit. Argon2id. **Почему не JWT:** мгновенный отзыв, нет утечки прав в токене, проще для многоорганизационной модели. MFA позже (ТЗ §13) — таблица `user_mfa` добавится миграцией, контракт сессии не меняется. Сброс пароля/письма — блокируется Q3.

### ADR-004 Границы модулей
`import-linter` контракты в CI: `domain` не импортирует `infrastructure`/`api`; модуль не импортирует `infrastructure` чужого модуля; слоистая зависимость по таблице в `01-architecture.md`. Нарушение — падение CI.

### ADR-005 Tenant isolation
Двойная защита: (1) репозитории требуют `OrgContext`; (2) RLS-политики `organization_id = current_setting('app.current_org')::uuid`, `SET LOCAL` в начале каждой транзакции запроса; роль приложения без `BYPASSRLS` и не владелец таблиц, миграции — отдельная роль. **Тест-обязательство:** для каждого тенантного ресурса — тест cross-tenant read/write/list/id-guessing, плюс тест «SQL без контекста возвращает 0 строк». **Риск:** пул соединений и `SET LOCAL` — используем только транзакционный режим; тест на утечку контекста между запросами.

### ADR-006 Sync-сессии SQLAlchemy
Транзакционная корректность и блокировки (`SELECT … FOR UPDATE`) важнее максимального I/O-параллелизма; FastAPI выполняет sync-эндпоинты в threadpool. Нагрузочные цели ТЗ §14 (p95) пересмотрим на этапе 9; смена на async — локальная в persistence-слое.

### ADR-007 Очередь задач
Выбрать один вариант (ТЗ §6). **Dramatiq + Redis**: проще конфигурация, ретраи и лимиты «из коробки», меньше скрытого поведения, чем у Celery. Задачи идемпотентны (ключ задачи в БД), статусы — в БД, а не в Redis. Появляется на этапе 3; до тех пор не подключаем.

### ADR-008 Деньги и количества
Только `Decimal`/`NUMERIC`. Линтер-правило запрещает `float` в модулях учёта; Pydantic-схемы принимают деньги **строкой** (в JSON), фронтенд не считает деньги (отображает серверные значения). Валюта — всегда рядом с суммой. Точность и режим округления — **Q6**, до ответа в код не зашиваются (параметр в одном модуле `platform/money`).

### ADR-009 Межмодульные события
По умолчанию — прямой вызов публичного application-сервиса в той же транзакции. Для побочных эффектов (уведомления, постановка в очередь) — transactional outbox (`outbox_event`, добавится миграцией с этапа 3), чтобы не терять и не дублировать события.

### ADR-010 Аудит
Таблица `audit_event` append-only (триггер, права роли). Запись в той же транзакции. Секреты/пароли/токены в `before/after` не попадают (allowlist полей на каждое событие). Просмотр — право `audit.read`.

### ADR-011 Идемпотентность
POST-операции, создающие или проводящие учётные записи, требуют `Idempotency-Key`. На этапе 1 применяется к созданию организации и приглашений; общий механизм — в `platform`. Для проведения (этапы 4–5) дополнительно естественные уникальные ограничения в БД (`UNIQUE(source, kind)`), а не только ключ.

### ADR-012 Неизменяемость учёта
Проведённые движения/проводки — без UPDATE/DELETE (триггеры + права роли). Исправление: сторно/корректирующая запись со ссылкой на оригинал. Закрытый период блокирует вставку на уровне БД и приложения.

### ADR-013 Интеграции
Контракт `IntegrationAdapter` (auth, capabilities, pagination, rate-limit, retries, webhooks, cursor, error mapping). Статусы подключения: `NOT_CONFIGURED`, `MOCK`, `CONNECTED`; UI показывает статус бейджем. **До получения официальной документации и тестовых credentials конкретные адаптеры Multibank/Faktura.uz/Didox не пишутся даже как «предположения»**; допускается только Generic File import (CSV/XLSX), который не требует внешнего API.

### ADR-014 AI
Выход LLM — только JSON по Pydantic-схеме; невалидный → `FAILED`/ручной ввод, не «починка на лету». Копилот — только типизированные read-only tools с проверкой org+прав; документы и внешний текст — недоверенные данные (разделение каналов, лимиты, фильтрация). AI не имеет connection string БД. Провайдер LLM/OCR не выбран — **Q10**; контракт `AIProvider` позволяет подключить любого.

### ADR-015 Frontend
Next.js App Router, TypeScript strict, Tailwind с дизайн-токенами из ТЗ §5 (CSS-переменные), Radix-примитивы для доступности, TanStack Query, Zod для форм (серверная валидация остаётся источником истины). Типизированный API-клиент генерируется из OpenAPI. i18n-каркас (`ru` основной) с самого начала, чтобы не переписывать строки позже — **Q7**.

### Поправки по итогам среза 1.1
- **ADR-015:** вместо Tailwind использован обычный CSS с токенами (`globals.css`) — проще на старте, обратимо. Шрифт Inter не подключён (системный стек), чтобы сборка не зависела от внешних загрузок.
- **ADR-011 (1.2):** для приглашений `Idempotency-Key` не используется — сохранённый ответ содержал бы секретный токен; защита от дублей — частичный уникальный индекс «одно действующее приглашение на (организация, email)».
- **ADR-011:** ключ идемпотентности привязан к пользователю; проигравший гонку получает 409 и повторяет запрос.
- **ADR-007/Redis:** Redis не поднимается, пока нет фоновых задач (этап 3).

### ADR-016 Качество
Definition of Done из ТЗ §16 и §21. CI на каждом PR: ruff, mypy --strict, pytest (unit+integration+security+invariants), ESLint, `tsc --noEmit`, Vitest, Playwright, import-linter, `pip-audit`, `npm audit`. Отчёт этапа — `docs/reports/stage-N.md` с фактическим выводом команд.
