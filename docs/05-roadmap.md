## 3. Этап 1 — Foundation: нарезка на вертикальные срезы

Каждый срез завершён по Definition of Done (ТЗ §16): UI + API + БД + права + тесты + состояния UI + логи + документация, без заглушек. После **каждого** среза — отчёт и остановка.

### Срез 1.1 — «Владелец регистрируется, создаёт организацию и входит» (предлагаемый ПЕРВЫЙ шаг)
Включает минимальный каркас: репозиторий, Docker Compose (postgres, backend, frontend), `.env.example`, Alembic, CI-пайплайн, `/health` `/ready`, OpenAPI, единый формат ошибок, correlation-id, структурные логи, токены дизайн-системы и App Shell (только реально существующие пункты), аудит, идемпотентность создания организации, RLS.

**Критерии приёмки 1.1** (все проверяются командами, вывод будет показан в отчёте):
1. `docker compose up` (или локальный запуск по README — Q1) на чистой машине поднимает БД, применяет миграции, стартует API и UI; `GET /ready` = 200 только при доступной БД.
2. Регистрация (email+пароль) → вход → cookie-сессия HttpOnly; выход отзывает сессию (повторное использование токена = 401).
3. Создание организации (идемпотентно по `Idempotency-Key`; повтор не создаёт вторую); создатель становится `owner`; в одной транзакции пишутся организация, членство, `audit_event`.
4. Переключатель организаций показывает только организации пользователя; `org_id` из заголовка/пути, на который нет членства → 403/404 (без утечки существования).
5. Пароль хранится Argon2id; токен сессии — только хэш; в логах и audit нет паролей/токенов (тест).
6. Троттлинг входа: N неудачных попыток → 429 (параметры в конфиге).
7. **Tenant isolation:** автотесты cross-tenant (API-уровень) + RLS-тест (прямой SQL с ролью приложения без контекста = 0 строк; с контекстом A не видит B; UPDATE/INSERT чужого org отклоняются).
8. `audit_event` нельзя изменить/удалить (тест на триггер и права).
9. Состояния UI: loading/empty/error/success для экранов входа, регистрации, создания организации, главной.
10. Проверки зелёные: `ruff`, `mypy --strict`, `pytest`, `import-linter`, ESLint, `tsc`, Vitest, Playwright (сценарий регистрация→организация→выход→вход), `pip-audit`/`npm audit` без critical.
11. README описывает запуск «с нуля» и проверен на чистом клоне.

### Срез 1.2 — Участники, роли и права (RBAC)
Роли (§5) заполняются миграцией; приглашение по одноразовой ссылке (без почты, честно подписано); принятие приглашения; смена роли, приостановка; защита «≥1 владельца»; `require(permission)` на всех эндпоинтах; скрытие пунктов UI по правам **и** серверный отказ.
**Приёмка:** матрица тестов «роль × эндпоинт × ожидаемый код»; нельзя понизить/удалить последнего владельца (конкурентный тест); приглашение одноразово и истекает; все изменения ролей в аудите; cross-tenant тесты для членств/приглашений.

### Срез 1.3 — Просмотр журнала аудита и безопасность профиля
Экран аудита (право `audit.read`, фильтры, пагинация, correlation_id); смена пароля; список активных сессий и «выйти везде».
**Приёмка:** аудит фиксирует входы/неудачи/смену ролей/смену пароля; пагинация и фильтры покрыты тестами; пользователь без права не видит и не получает данные.

**Что в этапе 1 НЕ реализуется:** письма и сброс пароля (Q3), MFA, SSO, справочники, документы, любая учётная логика, AI. Эти пункты не присутствуют в UI.

## 7. Риски

| Риск | Серьёзность | Митигация |
|---|---|---|
| Бухгалтерские/налоговые правила неизвестны | Высокая | Этап 5 блокирован; модель правил версионируема; в UI/доках нет заявлений о юридической точности |
| Нет документации API Multibank/Faktura.uz/Didox | Высокая | Не выдумываем; статус `NOT_CONFIGURED`; Generic File import |
| Утечка данных между организациями | Критическая | ADR-005: два слоя + обязательные cross-tenant тесты в CI |
| Двойное проведение / гонки | Высокая | Идемпотентность + `UNIQUE` + блокировки + конкурентные тесты |
| Prompt injection через документы | Высокая | ADR-014; отдельный набор тестов на этапе 8 |
| Сложность RLS с пулом соединений | Средняя | `SET LOCAL` в транзакции + тест на утечку контекста |
| Резидентность данных / закон о персональных данных | Высокая | Q4, юридическая проверка до prod; compliance не заявляем |
| Стоимость/качество OCR и LLM для узбекских/русских документов | Средняя | Метрики точности по ТЗ §14; абстракция провайдера; ручная проверка всегда |
| Объём проекта (одиночный разработчик + ИИ) | Средняя | Строго вертикальные срезы, остановка на каждой контрольной точке |
